# AI SDR — план доработки для портфолио

Обновлено: 2026-10-05. Интерфейс этапа 1 переработан: один основной Compose, отдельная страница Examples с двумя встроенными WebM-роликами, расходы в модальном окне с размытием и внешним крестиком. Светлая/тёмная/системная темы сохранены. Общий блок результата и элементы навигации имеют суперэллиптические углы с fallback. Playwright подключён, интерфейс проверяется в реальном Edge. Состояния будущего streaming вынесены в общий компонент и reducer; фактические запросы к API пока не подключены. Этап 0 целиком не выполнялся; Python-ядро не менялось.

## Цель и границы первой версии

Веб-приложение для исследования компании и подготовки обоснованного персонализированного письма с проверкой человеком. Пользователь задаёт компанию, своё предложение, роль получателя, язык и тон; получает факты с источниками, стратегию, редактируемое письмо и прозрачные показатели времени и стоимости.

Фронтенд: React + TypeScript + Vite. API: FastAPI. Оркестрация: существующий Python/LangGraph. Для первой версии — SQLite с миграциями и постоянным хранилищем при размещении. Отдельная предварительная работа пользователя в Figma не требуется: дизайн разрабатывается на рабочем экране с реалистичными демонстрационными данными.

Первая версия не включает автоматическую рассылку, CRM-интеграции и многопользовательскую организационную модель. По уточнению пользователя предусмотрены допуск по аккаунту, три реальные пробные попытки с видимым остатком и предложение купить доступ после исчерпания. Авторизацию и серверный учёт проб подключить на этапе 4; платёжный сценарий выбрать и реализовать перед платной публикацией на этапе 6. Ключи остаются на сервере. Существующий Streamlit остаётся временным способом реального запуска до подключения React.

## Метрики и деньги

Учёт начинается на этапе 2, до сравнительных запусков. На этапе 1 окно расходов показывает отсутствие данных. Вымышленные суммы удалены; числа появятся только после подключения учёта API. Расходы не размещать на главном экране.

- Для каждого вызова сохранять `run_id`, этап, номер попытки, provider/request ID при наличии, запрошенную и возвращённую модель, effort, версию промпта, время начала/окончания, статус и usage.
- Токены: входные, кэшированные входные, запись кэша при наличии такого тарифицируемого счётчика, выходные, reasoning как детализация выходных, итог. Использовать метаданные API, а не длину текста письма.
- Reasoning-токены не суммировать с выходными повторно. Категории кэша нормализовать по семантике API, чтобы одни входные токены не учитывались дважды.
- Стоимость: LLM отдельно, Tavily отдельно, итог. Для поиска хранить операции/кредиты и переводить их в деньги по выбранному тарифу. Пока тариф неизвестен — показывать кредиты и неполную оценку, а не нулевую стоимость.
- Сохранять версию тарифной таблицы, валюту USD, дату тарифа и режим обслуживания. Учитывать различия моделей, порогов контекста и режимов, применимых к конкретному вызову. Не пересчитывать исторические расходы новым тарифом незаметно для пользователя.
- Учитывать все вызовы с доступными usage, включая переписывания и оплачиваемые попытки. Если usage после сбоя неизвестен, показывать неполноту данных; не утверждать, что стоимость равна нулю.
- В интерфейсе: сумма за запуск, раскрываемая разбивка по этапам/попыткам, итог за день и выбранный период, средняя стоимость успешного результата, время обработки и количество повторов. Суточные границы — Europe/Berlin; время хранения — UTC.
- Денежные суммы обозначать как расчётную стоимость, а не сверенный счёт провайдера. Расходы на разработку в Codex и хостинг в метрики API-запуска не входят.
- Добавить лимит попыток и выходных токенов, бюджет запуска/дня и проверку бюджета до очередного вызова с запасом. Это ограничение оценочных затрат, а не гарантия точного потолка счёта при неизвестном usage или параллельных вызовах.
- Проверить арифметику тарифов, отсутствие двойного учёта, агрегацию за день и обработку неизвестного usage отдельными целевыми тестами.

## Модели приложения

Не менять модель только ради новизны. База сравнения — текущая `gpt-5.4-mini`; кандидаты — `gpt-6-luna` и `gpt-6-sol`. Проверить доступность API на аккаунте при реализации. Каталог уже также содержит GPT-6.1 Sol; его можно включить дополнительным кандидатом, если это оправдано, не подменяя запрошенное сравнение с GPT-6 Sol.

Первый эксперимент: Luna low/medium для извлечения фактов и проверки; Luna medium и Sol low/medium для стратегии и письма. Назначения предварительные, выбор зависит от результатов. Обеспечить общий слой вызовов, конфигурацию по этапам, совместимые параметры и Responses API там, где это необходимо. Не переносить `temperature=0.5` без проверки совместимости.

На 2026-10-04 официальные страницы указывают для Standard и короткого контекста следующие цены за 1 млн токенов:

| Модель | Обычный вход | Кэшированный вход | Запись кэша | Выход |
| --- | ---: | ---: | ---: | ---: |
| GPT-6 Luna | $0.10 | $0.01 | $0.125 | $0.50 |
| GPT-6 Sol | $2.00 | $0.20 | $2.50 | $10.00 |

Это справочные ставки, не полный калькулятор. Перед реализацией и сравнением перепроверить тарифы, пороги контекста, выбранный режим и применимые надбавки. Более низкая цена за токен не доказывает более низкую стоимость качественного результата.

## Проверка качества

Подготовить 20–30 случаев: известные и небольшие компании, неоднозначные названия, мало информации, неверный сайт, несоответствие нашему продукту, разные языки. Часть случаев оставить для итоговой проверки после настройки промптов. Для честного сравнения моделей использовать одинаковые сохранённые источники; живой поиск проверять отдельно. Повторить часть запусков для оценки разброса.

Измерять подтверждаемость фактов, релевантность предложения, полезность и естественность письма по ручной шкале, соблюдение ограничений, корректность отказов, частоту ошибок, повторы, медианное время и стоимость успешного результата. Не выдавать оценку того же LLM за независимое доказательство качества. Не заявлять рост конверсии без реальной кампании.

## Передача работы между чатами

В рамках одного этапа продолжать тот же чат: визуальные правки после первого экрана, исправление ошибки после теста и проверка исправления должны сохранять свой контекст. Менять чат на завершённой границе этапов, а не по числу сообщений. Смена effort сама по себе не повод менять чат.

Перед переходом обновить этот план и `HANDOFF.md`: выполненные этапы, решения, текущая ветка и коммиты, незакоммиченные изменения, проверенные команды и результаты, известные проблемы, следующий шаг. Не помещать туда ключи. `HANDOFF.md` создан после реализации первого интерфейса.

Стартовое сообщение нового чата:

> Продолжаем AI SDR. Прочитай ROADMAP.md, HANDOFF.md и применимые AGENTS.md, проверь git status. Продолжай с этапа N, учитывая выполненные проверки и текущие изменения. Объясняй ключевые решения так, чтобы я мог представить проект заказчику.

Рекомендация Astra: medium для обычной реализации и полировки, high для архитектуры, интеграции и AI-логики, xhigh точечно для сложной диагностики или итогового аудита. Постоянные max/ultra в этом проекте не планируются. Настройки разработки и настройки API приложения независимы.
